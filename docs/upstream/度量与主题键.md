## 0. 两条通道，以及「数字」到底从哪来

上游的每个度量都有两个来源，复刻时必须两个都建模：

1. **代码里的兜底常量** —— `JBUI.CurrentTheme.*` 的 `defaultXxx()` 方法。
2. **主题键覆盖** —— `UIManager.get("键名")`，由 `*.theme.json` 灌进去。

典型形状（`platform/util/ui/src/com/intellij/util/ui/JBUI.java:1170-1180`）：

```java
public static int headerHeight() { return getInt(headerHeightKey(), defaultHeaderHeight()); }
public static String headerHeightKey() { return "ToolWindow.Header.height"; }
public static int defaultHeaderHeight() { return 41; }
```

`getInt` 就是查 `UIManager`，查不到用兜底（`JBUI.java:2808-2811`）。
**所以「41」不是主题里的数，是代码里的数**；主题只是可以改它。

第三件事：**所有像素值都要过 `JBUI.scale` / `JBUIScale.scale`**（按用户缩放倍率）。
本文表里的数字一律是**未缩放值**（unscaled），与上游源码写法一致。

### 5.1 停靠面板的边框：外边框与内边框是两套

出处：`platform/platform-impl/src/com/intellij/toolWindow/InternalDecoratorImpl.kt` 的
`InnerPanelBorder`（`:670` 起）。

先看 insets 怎么算（`:747-824 · getBorderInsets`）：

- 非内部形态（FLOATING / WINDOWED，见模型文档 §2 的 `isInternal`）直接返回空 insets（`:751-753`）。
- `bottom` **恒为 0**（`:759`）。
- `top`：不贴分隔条、不是 FLOATING、且贴着工具窗口上沿 → 1（`:757-758`）。
- `left`：不贴分隔条、**anchor == RIGHT**、且贴着左沿 → 1（`:760-761`）。
- `right`：不贴分隔条、**anchor == LEFT**、且贴着右沿 → 1（`:762-763`）。

「贴不贴分隔条 / 贴不贴边」不是算出来的角度，而是沿着组件树往上爬一遍得到的一组标志
（`:835` 起 `getSideProperties`，枚举 `SideProperty` 在 `:1162-1173`：
四个 `*_DIVIDER` + 四个 `*_TOOL_WINDOW_EDGE`）。

**外边框**（`:676-712 · doPaintExternalBorder`）：

- 顶边的颜色分两种：anchor == BOTTOM，或者（anchor == RIGHT 且 isSplit）→ `ToolWindow.borderColor`；
  否则 → `MainToolbar.borderColor`（`:698-704`）。
- 其余边一律 `ToolWindow.borderColor`（`:705`）。
- **每条边画的是两条相邻的 1px 线**，不是一条（`:705-709` 等处成对的 `LinePainter2D.paint`）。

**内边框**（`:726-745 · doPaintInternalBorder`）：颜色是 `ToolWindow.background()` ——
它不是「边框」，是**用背景色盖掉一像素**。触发条件很窄（`:790-822`）：
只有当 `JBColor.border()` 恰好等于编辑器全局配色的默认背景色时才可能画，
用来处理「工具窗口贴着编辑器、两边背景一样、边界糊在一起」的五种情形（注释 `:793-800` 自己列了）。
画的时候还要按外边框是否存在错开 1~2 px（`:737`、`:741`）。

复刻时的取舍：**外边框照抄，内边框先不做** —— 它是为「工具窗口里嵌了个编辑器样式的组件」
这一特定场景打的补丁，触发条件依赖编辑器配色，本项目现在还没有编辑器。

## 7. 主题是怎么解析出来的

出处：`platform/platform-impl/src/com/intellij/ide/ui/UITheme.kt`、`UIThemeBean.kt`、`uiThemeParser.kt`。

1. **颜色别名**：`colors` 段里的名字（`Gray13`、`Blue4`…）在写进 defaults 前先查表替换
   （`UITheme.kt:92-100`）。
2. **`*.` 通配**：键以 `*.` 开头时，取后缀（含点），把**当时 defaults 里所有以该后缀结尾的键**
   全部覆盖掉，同时注册成 pattern 供后续查找命中（`UITheme.kt:103-112`）。
   —— 注意是「当时已存在的键」，所以**加载顺序会影响结果**。
3. **父主题**：`parentTheme` 指的那份的 `ui` / `colors` / `icons` 等 map 会被合并进来，
   子主题同名键胜出（`UIThemeBean.kt:490-497 · importFromParentTheme`）。
   实际链条：`expUI Light → IntelliJ(intellijlaf) → Darcula`；`expUI Dark → Darcula`。
4. **新 UI 的强制项**：如果主题没写，强行补
   `ToolWindow.Button.selectedBackground = #3573F0`、`ToolWindow.Button.selectedForeground = #FFFFFF`
   （`UIThemeBean.kt:472-482 · putDefaultsIfAbsent`），注释明说**这两个键不许靠 `*` 通配拿到**。
   注意这个 `#3573F0` 与 expUI 里写的 `#3574F0` **差一位**，两处都是有意写死的。
5. **值的类型按键名后缀猜**（`uiThemeParser.kt:20-45`、`:167-180`）：
   `Insets` / `.insets` / `padding` → 内边距；`Size` / `.size` → 尺寸；
   `Border` / `border` → 边框；`Width` / `Height` → 数字；`AllIcons.` 开头 → 图标。
   判断前先去掉 `.compact` 后缀（`:26`、`:169`）。

## 8. 缩放：`JBUI.scale` 到底做了什么

出处：`platform/util/ui/src/com/intellij/ui/scale/JBUIScale.kt`。

```kotlin
fun scale(value: Float): Float = value * userScaleFactor.value          // :391-393
fun scale(i: Int): Int = (userScaleFactor.value * i).roundToInt()       // :399-401
```

两条要点：

1. **整数版本是四舍五入**（Kotlin 的 `roundToInt`，`.5` 向上取），不是截断。
   40 在 1.25 倍下是 50，41 是 51；13 在 1.75 倍下是 `22.75 → 23`。
   逐像素对齐必须照抄这个取整，否则会差 1 px。
2. 字体是另一套（`:415-426 · scaleFontSize`），有两个硬编码特例，且结果是**截断**不是四舍五入：

   | userScaleFactor | 字号乘数 |
   |---|---|
   | 1.25 | **×1.34** |
   | 1.75 | **×1.67** |
   | 其它 | ×userScaleFactor |

### 8.1 userScaleFactor 从哪来

`computeUserScaleFactor`（`:303-347`）：

- JVM 属性 `ide.ui.scale` 给了就直接用（`:304-309`）；
- 否则：JRE 托管 HiDPI 时基准取 `1f`，IDE 托管 HiDPI 时取系统缩放（`:311-318`）；
- `-Dhidpi=false` → 直接返回 `1f`（`:327-329`）；
- **离散化**：`discreteScale`（`:490-495`）把缩放对齐到 **0.25 的整数倍**
  （`DISCRETE_SCALE_RESOLUTION = 0.25f`，`:37`），默认四舍五入，
  Registry `ide.scale.discrete.take.floor` 打开时改成取下整；
- Linux + 恰好 1.25 + `DEF_SYSTEM_FONT_SIZE == 12` → 强制回 `1f`（`:339-346`，
  注释说 Unity/Gnome 默认字号 15，1.25 在 Linux 上效果差）。

`DEF_SYSTEM_FONT_SIZE` 默认 **12f**（`:113`），`getFontScale(size) = size / 12`（`:270`）。

### 8.2 IDE 缩放（Ctrl+滚轮那个）怎么接进来

这是另一条路，最后汇到同一个 `userScaleFactor`：

`UISettings.currentIdeScale`（`UISettings.kt:570-578`）= 演示模式时取 `presentationModeIdeScale`，
否则取 `ideScale`，后者默认 **1f**（`NotRoamableUiSettings.kt:172`）。

换主题 / 改缩放时走 `LafManagerImpl.kt:852-880 · patchLafFonts`：

```
fontSize        = 基准字号 × currentIdeScale        // :861
userScaleFactor = getFontScale(fontSize)            // :865，即 fontSize / 12
                  （用 Inter 字体时是 fontSize / INTER_SIZE）
setUserScaleFactor(userScaleFactor)                 // :866
```

**所以 `JBUI.scale` 的倍率归根到底是从「字号」推出来的，不是直接从 DPI。**
IDE 缩放先改字号，字号再反推出倍率。

而 `setUserScaleFactor`（`JBUIScale.kt:286-301`）内部又调了一次
`computeUserScaleFactor(scale)`，**所以这条路一样会被离散化到 0.25 的整数倍**
（JVM 属性 `ide.ui.scale` 给了调试值时除外，`:289-295`）。

**结论：缩放倍率不是任意小数，而是 0.25 的整数倍。** 复刻时把倍率建成离散值，
测试就能穷举 1.0 / 1.25 / 1.5 / 1.75 / 2.0 这几档。

## 9. 紧凑模式（compact / UIDensity）

一直在各处出现的 `.compact` 后缀，**切换点在这里**：
`platform/platform-impl/src/com/intellij/ide/ui/laf/LafManagerImpl.kt:1446-1474 · applyDensityOnUpdateUi`。

```kotlin
if (newDensity == UIDensity.COMPACT) {
  val compactValues = mutableMapOf<String, Any>()
  uiDefaults.forEach { key, value ->
    if ((key as? String?)?.endsWith(".compact") == true) {
      compactValues[key.removeSuffix(".compact")] = value
    }
  }
  uiDefaults.putAll(compactValues)
}
```

即：**遍历整张 UIDefaults，把所有 `X.compact` 的值盖到 `X` 上**。
不是查询时判断，而是切换密度时**一次性改写整张表**。
`ui.density` 这个键本身也存在表里，值相同就直接返回（`:1448-1453`），
注释说明原因是重复套用会破坏 HiDPI 可缩放的值。

密度开关：`UISettings.uiDensity`，默认 **`UIDensity.DEFAULT`**
（`platform/editor-ui-api/src/com/intellij/ide/ui/UISettingsState.kt:144`）。

同一个函数旁边还有一条同构的机制（`LafManagerImpl.kt:1477-1488 · applyAltColors`）：
`differentToolwindowBackground` 打开时，把所有 `alt.X` 的值盖到 `X` 上。
该开关默认 **false**（`UISettingsState.kt:80`），且本轮审到的四份主题里
**没有任何 `alt.` 键**，所以现在是空转。

### 9.1 紧凑模式下工具窗口相关的值

全都定义在 `platform/platform-resources/src/themes/darcula.theme.json` —— 注意它是
**两条主题链共同的根**（expUI Light → IntelliJ → Darcula；expUI Dark → Darcula，见 §7.3），
所以新 UI 也吃这份值。

| 键 | 默认 | 紧凑 |
|---|---|---|
| `StripeToolbar.Button.size` | 40,40 | **32,32** |
| `StripeToolbar.Button.iconSize` | 20 | **16** |
| `StripeToolbar.Button.leftStripeIcon.padding` | 5,5,5,5 | **4,4,4,4** |
| `StripeToolbar.Button.rightStripeIcon.padding` | 5,5,5,5 | **4,4,4,4** |
| `StripeToolbar.Button.leftStripeIconWithName.padding` | 5,5,5,5 | **3,3,3,3** |
| `StripeToolbar.Button.leftStripeTextOffset` | 0 | 0 |
| `StripeToolbar.Button.rightStripeTextOffset` | 0 | 0 |
| `ToolWindow.Header.height` | 41 | **31** |
| `ToolWindow.Header.fontSizeOffset` | 0 | **-1** |
| `EditorTabs.underlineHeight` | 3 | 3 |

一处不对称，照抄时别「顺手补齐」：**`rightStripeIconWithName.padding.compact` 不存在**，
只有 left 那一半有。所以紧凑 + 显示名字时，右条带的图标 padding 仍然取默认的 5。

代码里另有两处不走主题键的紧凑分支：

- 按钮圆角：`JBUI.java:1358-1360 · stripeButtonArc(compact)` → 紧凑 **8**，否则 12；
- 条带最小宽度：`ResizeStripeManager.kt:138-141` → 紧凑 **33**，否则 40；
- 条带按钮名字的左右 padding：`SquareStripeButton.kt:255` → 紧凑 **4**，否则 6。

这三处读的是 `UISettings.compactMode`，而它就是 `uiDensity` 的一个别名
（`UISettings.kt:261-265`）：

```kotlin
var compactMode: Boolean
  get() = uiDensity == UIDensity.COMPACT
  set(value) { uiDensity = if (value) UIDensity.COMPACT else UIDensity.DEFAULT }
```

**同一个开关，两种读法**：主题键走「切换时改写整张表」，代码分支走这个布尔属性。
复刻时用一个 `IsCompact` 即可。

## 10. 复刻到 Avalonia 的直接结论

1. 度量建成「代码常量 + 可被主题键覆盖」的两层，别把 41、40、20 直接写进控件模板。
   常量表按 §1–§5 落一份，键名按 `themeMetadata.json` 落一份。
2. 所有未缩放值统一走一个 `Scale(int)` 入口，不要在各处 `* scaleFactor`；
   取整必须是**四舍五入**，字体另走一套带特例的换算（§8）。
   缩放倍率建成 0.25 的整数倍的离散值。
3. 颜色查找要实现「键 → 兜底键 → 代码字面量」的三级回落链，
   这是 `JBColor.namedColor(key, fallback)` 的语义（例：`stripeBackground` 回落到 `background`）。
4. `*` 通配和 `parentTheme` 合并可以先不做——但**主题文件里要能写全键**，
   即不能依赖通配去覆盖，否则会踩 §7.4 那个坑。
5. 分组分隔符（§1.2）与 BOTTOM 组的倒序（§1.3）容易漏，先写测试卡住。
6. 紧凑模式按 §9 做成「切换时改写整张表」，不要做成查询时判断 —— 上游就是前者，
   而且它顺带解释了为什么 `.compact` 只是个普通键后缀。
