# 宿主接入指南

这份文档只回答一个问题：**哪些事归库，哪些事归你**。

完整外壳示例见 `samples/Piccolo.Forge.Sample.ExpUi`、`.Islands` 与 `.Mvvm`；控件目录是 `.Sample`。
真要照抄就抄那个文件，别抄这里（这里为了讲清楚做了删减）。

---

## 0. 三分钟版本

```csharp
// ① 你的面板：继承 ToolWindowPanel，它就是一块停在边上的工具窗口
internal sealed class ProjectTool : ToolWindowPanel
{
    public ProjectTool() : base("Project") { Title = "项目"; Icon = myIcon; }
}

// ② 外壳 VM：宿主的接入点
var shell = new ToolWindowShellViewModel();

// ③ 登记：把面板交出去，只说「停哪条边、哪一半」
shell.Add(new ProjectTool(), ToolWindowAnchor.Left);
shell.Add(new StructureTool(), ToolWindowAnchor.Left, isSplit: true);

// ④ 控件接上就完事
var frame = new ForgeControl();
frame.Attach(shell);          // 等价于 frame.Shell = shell
```

⚠ **还有一句不能忘 —— 装主题**（在 `Application` 起来时、外壳控件挂树之前）：

```csharp
// 主题入口安装一次，选择的 Family 需有对应资源包。
ForgeThemeManager.Apply(app, new ForgeTheme { Family = ForgeThemeFamily.ExpUi });
```

不装就没有 `ControlTheme`，控件**什么都不画且不报错**。详见 §5.0a。

**或者整块写在 XAML 里** —— `Shell` / `Editor` 都是可绑定属性（对位 Dock 的
`<DockControl Layout="{Binding Layout}"/>`）：

```xml
<forge:ForgeControl Shell="{Binding Shell}">
  <forge:ForgeControl.EditorContent>
    <forge:ForgeEditorControl Editor="{Binding Editor}"/>
  </forge:ForgeControl.EditorContent>
</forge:ForgeControl>
```

⚠ **只有"接哪个 VM"能写进 XAML。** 外观里的取色回调、外部窗体工厂是委托，仍得在 C# 里给
（Dock 那边同样如此——它的 `HostWindowLocator` 是个 `Func` 字典）。

配色、条带按钮落位、开合互斥、拖拽、存档格式——都不用你写。

## 1. 边界

| 归库 | 归你 |
|---|---|
| 面板的**身份**（id / 标题 / 图标字段） | 图标画什么 |
| 面板**停在哪**（anchor + isSplit）与按钮落位 | 一开始摆哪 |
| 「一格一个可见窗口」的互斥（§7.1） | 被挤掉之后做什么（暂停采集之类） |
| 开合、激活、拖拽换位、拖分隔条改大小 | — |
| 条带 / 标题条 / tab 的全部度量与配色 | — |
| 明暗跟随宿主的变体自动切 | 宿主自己的明暗设置 |
| 存档的**格式**（`ToolWindowLayoutSerializer`） | 存到哪、什么时候存 |
| 面板内容的**槽**（`Content` 是 `object`） | 内容 VM、视图怎么解析 |

一句话：**库管"工具窗口这套机制"，你管"里面装什么、什么时候动"。**

### 为什么内容是 `object`

`ToolWindowViewModel.Content` 和 `IForgePanel.Icon` 都是 `object`。
控件库不认识你的视图，也不该替你选图标库。你塞 VM 进去，
视图由**你自己的** ViewLocator / DataTemplate 解析——库这边就是个 `ContentControl`。

## 2. 选哪个包

面板基类有**两种绑定**，二选一：

| 包 | 依赖 | 什么时候选 |
|---|---|---|
| `Piccolo.Forge.Mvvm` | 无 MVVM 框架 | 默认选这个 |
| `Piccolo.Forge.Mvvm.CommunityToolkit` | CommunityToolkit.Mvvm | 你的派生面板要用 `[ObservableProperty]` / `[RelayCommand]` |

两个包里的类**同名同形**（`ForgePanelBase` / `ToolWindowPanel` / `EditorPanel`），
换绑定只用改 `using`。

这个分法抄的是 Dock.Avalonia：`Dock.Model` 不引框架只出接口，
`Dock.Model.Mvvm` 才依赖 CommunityToolkit 出基类，另有 `Dock.Model.Avalonia`
是同一套模型的另一种绑定。**接口在中立包、基类按框架分包**——
不这么分，库一旦自带一个 `ObservableObject`，宿主的源生成器就会失灵
（LDVision 接入时当场撞过 CS0104）。

`Piccolo.Forge.Model` 和 `Piccolo.Forge.Mvvm` 都**不引 Avalonia、不引任何 MVVM 框架**，
有用例检查程序集引用钉住这条。

## 3. 面板的两种类型

```csharp
public interface IToolWindowPanel : IForgePanel;   // 停在四条边上
public interface IEditorPanel     : IForgePanel;   // 活在中间那块
```

两个都是**空标记接口**——照 Dock 的 `ITool`（那个接口也是 0 个成员）。

**继承哪个类就决定了停靠方式**，你不用在每处再说一遍；
而且「把编辑区面板停到侧边」**编译期就不成立**。

上游把两者放在不同的包（`wm` vs `fileEditor`），那是 IntelliJ 的分包方式；
**Forge 两块都做** —— 一个「Rider 形态」的库不带编辑区没法用。
编辑区的行为与数字同样照上游审，见 [编辑区](../upstream/编辑区.md)。

## 4. 位置怎么说

```csharp
shell.Add(panel, ToolWindowAnchor.Bottom, isSplit: true);
```

只有两个自由度：

- `anchor` —— 停哪条边（`Top` / `Left` / `Bottom` / `Right`）
- `isSplit` —— 同一条边被切成两半，占哪一半

**没有「四个角」这种东西。** 按钮画在哪根条带是**算出来的**
（`StripePlacementResolver.Resolve`）：

| anchor | isSplit | 面板停在 | 按钮画在 |
|---|---|---|---|
| Left | false | 左边上半 | 左条带上组 |
| Left | true | 左边下半 | 左条带上组（分隔符之后） |
| Right | false / true | 右边上 / 下半 | 右条带上组 |
| Bottom | **false** | 下边左半 | **左**条带下组 |
| Bottom | **true** | 下边右半 | **右**条带下组 |

最后两行是最容易搞错的地方：**anchor=Bottom 的面板停在下边，按钮却在左/右条带上**。
上游把「面板停在哪」和「按钮画在哪」分开，Forge 照做。详见
[工具窗口模型](../upstream/工具窗口模型.md) §1。

新 UI 没有 `Top` 条带，登记到 `Top` 会抛异常（上游的默认布局也构造不出 TOP）。

## 5. 你多半需要接的几件事

### 5.0a 装主题：引哪个包就是哪套，且**换主题要重启**

**包管"有哪些可用"，`Family` 属性管"用哪个"**（12.1.0 起）。入口类只有三个，
都在 `Piccolo.Forge.Avalonia`；族的资源在两个**纯资源包**里：

| 入口（`xmlns:forge="using:Piccolo.Forge.Avalonia"`） | 装什么 | 给谁 |
|---|---|---|
| `ForgeTheme` | 控件 + 外壳（完整基础主题） | 全都要的（对位 SemiTheme） |
| `ForgeControlsTheme` | 只有控件（也是完整基础主题） | 要 IntelliJ 控件、不用停靠的 |
| `ForgeShellTheme` | 只有外壳 | 已有基础主题、只要停靠的（基础主题排它前面） |

| 资源包 | 内容 |
|---|---|
| `Piccolo.Forge.Themes.ExpUi` | 经典 expUI 的色板 + 外壳模板 |
| `Piccolo.Forge.Themes.Islands` | Islands（圆角留缝、浮在"海"上）的 |

两个资源包互不依赖。只要一族的引一个；让用户挑的两个都引 ——
`Family` 选了没被引用的族，**启动即抛**，异常写明缺哪个包。装法二选一：

```xml
<Application.Styles>
    <forge:ForgeTheme Family="Islands"/>
    <!-- 族从配置来就写 Family="{x:Static local:Settings.Family}"，启动时求值一次 -->
</Application.Styles>
```

```csharp
ForgeThemeManager.Apply(app, new ForgeTheme { Family = settings.Family });   // 读完配置再装
```

DataGrid / ColorPicker 的模板在附加包（`Piccolo.Forge.Avalonia.DataGrid` / `.ColorPicker`），
与主题入口一起挂上即可 —— **先后无所谓**（色板键走 `DynamicResource`，两边的隐式 ControlTheme
也不撞类型）；漏装主题入口才会出问题：控件画得出来但没颜色，且不报错。
它们没有 `Family` —— 模板两档共用，颜色跟主入口选的族走，错档在结构上不可能。

两条路 `ForgeThemeManager.Current` 都认得出装的是哪族（它在 `Application.Styles` 里找实现了 `IForgeTheme` 的单元）。

代码装的时机是死的：**读完你自己的配置之后、外壳控件挂树之前**。装晚了首帧没有模板（什么都不画、
不报错）；装早了还不知道用户选的是哪一档。

⚠ **换主题要重启，这不是偷懒。** 实测（`ThemeSwapSpikeTests`）：运行时换掉
`Application.Styles` 里的单元，**已经挂在树上的控件不会重新解析 `ControlTheme`**，
翻明暗变体也不会。硬切的结果是最坏的一种：C# 侧按新族算几何取色、模板还是旧族画的。
所以设置页只写配置 + 提示重启（LDVision 就是这么做的）。

⚠ **两个开关必须同族**：装了哪套主题、`Appearance.Family` 是哪族。
不一致时 Debug 下会当场抛（`ForgeThemeManager.AssertConsistent`）——
它拦的正是"引的是 expUI、Family 却是 Islands"这种只在局部露馅、肉眼极难归因的状态。

语言与主题无关：`ForgeThemeManager.ApplyLocale(app, culture)` 装文案字典（见 §5.2）。

#### 添加第三个主题的步骤清单

这份清单能不能写短，本身就是 REQ-068 的架构验收。它是四步：

1. `ForgeThemeFamily` 加一个枚举值；
2. 新建工程 `Piccolo.Forge.Themes.<新名字>`，照着 `Piccolo.Forge.Themes.ExpUi` 复制
   （纯资源包，无代码）：`Colors.axaml`、`Controls.Colors.axaml`、`Shell.axaml`、`Themes/` 下全部外壳模板；
   入口不用新建 —— `Family` 枚举值加了，三个入口类自然认得（资源按 avares 约定名解析）；
   **缺哪个控件、缺哪个键，`ForgeThemeCompletenessTests` 当场报红并点名**；
3. `ForgePalette.ForTheme` 给新族返回一份配色；
4. 宿主引新包、装它。

**既有单元一行都不用动**。

### 5.0a2 换主题色：给一支种子色，别逐键抄

```csharp
ForgeThemeManager.Apply(app, new ForgeTheme
{
    Family      = ForgeThemeFamily.ExpUi,
    AccentLight = Color.Parse("#0064FA"),   // 亮色档的主题色
    AccentDark  = Color.Parse("#B8680F"),   // 暗色档的主题色（明暗本来就是两个设计决定）
});
```

色板里那一批跟着强调色走的键会全部跟着换 —— **控件那半 9 个 + 外壳那半每族 8 个**，明暗各一份。
不设（`null`）就用本族色板自带的强调色，与本属性存在之前逐字节一样。

**派生规则两条**：

| 档 | 哪些键 | 怎么算 |
|---|---|---|
| 实心填充 | 按钮主色、焦点环、勾选框、标签下划线、进度条、条带按钮选中底、面板标题条下划线 | **取种子原值**（alpha 随色板原值 —— Islands 那支全透明的下划线因此仍不可见） |
| 派生 | 列表/菜单/输入框的选中底、拖放落点与蒙版、Islands 的选中标签底 | **保住色板原本的明度 L**，饱和度按「种子 S ÷ 本族强调色 S」等比缩放，色相换成种子的 |

明度阶梯是主题作者调好的（哪支该浅、哪支该深、文字压上去够不够对比度），种子不该动它；
S 等比缩放是为了让**低饱和的种子**（想要一套灰调界面）能把那批浅底一起拉灰。
带 alpha 的键只换 RGB 段 —— 那个透明度是叠加强度，不是颜色。

> ⚠ **别再逐键覆盖。** 强调色的键分两套：控件那半**不带族**、类型是 `SolidColorBrush`；
> 外壳那半**带族**（`Forge.ExpUi.*` / `Forge.Islands.*`）、类型是 `Color`。两族明暗四档下来是
> **37 处色值**。手抄一遍不是配置，是把库的调色板复制了一份：漏一个键不报错，
> 症状是"面板里的选中条变了、**侧边栏条带按钮还是原来的蓝**"。LDVision 实测漏过一次，
> 种子键就是为它加的。

> ⚠ 想让**某一个**键脱离种子单独指定，仍然可以在宿主自己的 `Application.Resources` 里重定义同名键
> —— 宿主资源排在 Styles 的资源之前，照样赢。种子只管色板层。

> ⚠ 与 `Family` 不同，种子色**可以在运行期改**：它只换资源值，而颜色是 `{DynamicResource}` 取的，
> 已经挂树的控件会跟着变。（换族要重启是因为**模板**换了，那是另一回事。）
> 已经装着同族主题时再 `Apply` 一个带种子色的，种子色会被**接到已装的那套上**（不换 Styles，
> 免得已挂树的控件重新套模板）。

### 5.0 外观：一个对象，别设两遍

外框与编辑区是两个控件，但外观是**一份**。给外框设上，编辑区自动跟着：

```csharp
frame.Appearance = ForgeAppearance.Default with
{
    Family            = ForgeThemeFamily.Islands,   // 族（与明暗正交）
    PaletteResolver   = (family, variant) =>        // 想微调配色时才给
        ForgePalette.ForTheme(family, variant) with { IslandBorder = ... },
    IslandMetrics     = ForgeIslandMetrics.Default with { BorderWidth = 3 },
    HeaderTitleFontWeight = FontWeight.Black,       // 面板标题条 ┐ 同一件事
    TabTitleFontWeight    = FontWeight.Bold,        // 文档标签   ┘ 的两半
    HeaderHeight = 31,                              // 面板标题条 ┐ 同上
    TabRowHeight = 31,                              // 文档标签行 ┘
};
```

它是 record，改一处用 `with`：`frame.Appearance = frame.Appearance with { Family = … };`
——**整个对象换掉才有变更通知**，所以别指望改字段（也改不了，是 `init`）。

传播规则只有两条：

| 情况 | 怎么到手 |
|---|---|
| 编辑区摆在 `frame.EditorContent` 里 | **自动**（继承式附加属性 `ForgeChrome.Appearance`），你不用管 |
| 编辑区独立使用；文档浮出去的那些窗口 | 库显式传**整份**过去；你自己 new 的那个自己给一份 |

想让某块跟别处不一样，就在那个控件上单设一份——继承的常规规矩，不必再找开关。

> 早先这些是两个控件各一套的散装属性。代价是每样都要设两遍（漏一边 = 四边是岛、中间还是方角），
> 而库内部每个传播点还得手抄一遍——`FloatOut` 就抄漏过取色回调 / 字重 / 行高，
> 表现是文档浮出去之后描边没了、字重和行高变回默认。打成一个对象之后，漏抄在语法上不可能。

### 5.0a 面板宽窄是**像素**，不是比例

停靠区（`ForgeDockPane`）的边尺寸只有一套语义：**像素**。面板拉多宽就一直多宽，
窗口放大 / 全屏时增加的空间全部给中间的编辑区；窗口缩得比面板还窄时面板才跟着缩，
再拉回来又回到你拉的那个宽度。宿主不需要开任何开关。

> 这一条**有意偏离上游**：IntelliJ 的 `weight` 是占这条边的比例（`ToolWindowPane.kt:315-355`），
> 窗口一变宽两侧面板跟着一起变宽。IDE 里合理（两边装的是同样要长的树和列表）；
> 中间是一幅要尽量大的画面时，那就是在摊掉屏幕。

`weight` 只剩两处用场，**排布过程中不再经过它**：

| 场合 | 谁在动 |
|---|---|
| 某条边还没有像素记录（首次布局、读档、恢复默认布局之后） | 按 `weight` 播一次种 |
| 窗口改了大小 | 库按当前 pane 把像素反算成等价 `weight`，经 `ForgeDockPane.AnchorWeightRebased` 回抛，`ForgeControl` 写回台账（**只为存档**，写回来不会反过来改像素） |

宿主要知道的入口：

```csharp
frame.DefaultAnchorWidth = 350;       // 左右两边**默认**多宽（像素）；不设 = 按 weight 算
pane.SetAnchorSize(anchor, pixels);   // 直接定尺寸（库内部拖分隔条走的就是它）
pane.InvalidateAnchorSizes();         // 丢掉记录，下一轮按 weight 重新播种
```

`DefaultAnchorWidth` 只在这条边**还没有像素记录、且它的 weight 就是那份默认值**时起作用 ——
用户拉过的宽度、读回来的存档都是有主的值，不会被它盖掉。上下两条边不受影响。

`InvalidateAnchorSizes` 只在**布局意图真的换了**时调（读档 / 恢复默认布局 / 面板换边或开合），
`ForgeControl` 已经接在工具窗口的状态变更上了，宿主一般不用自己调。

> ⚠ 别再引入"像素 → weight → 排布时 floor 回像素"的往返：那一来一回带着量化误差，
> 窄尺寸下足够让边界每帧跳一格 —— 实机表现是"拖到小一点时标题栏一跳一跳，拖过某个宽度就好了"。

### 5.0b 按需面板：给工厂，别给实例

```csharp
shell.Add("Histogram", "直方图", ToolWindowAnchor.Bottom,
          () => new HistogramViewModel(),      // ← 第一次真被打开时才跑
          isSplit: true, icon: myIcon);
```

按钮从启动就全都在，实例等到面板真被打开才造。

⚠ **别自己去找「该造了」的时机**：用户点条带按钮走的是**库内部**的开合，
宿主插不上手。漏掉那条路的结果是「按钮点了、面板开了、里面是空的」——
不报错，只是空白，很难往「没人创建内容」上想。

### 5.1 面板不可见就别再干活

库给的是**信号**，策略你定：

```csharp
shell.StateChanged += (_, _) =>
{
    foreach (var vm in shell.ToolWindows)
        if (vm.Content is IPausable p) { if (vm.IsOpen) p.Start(); else p.Stop(); }
};
```

`IsOpen` / `IsActive` 都带属性变更通知，绑到 UI 上也行。

### 5.2 切语言

面板名：改面板自己的 `Title` 就够了，会自动跟到条带提示与标题条。
**别在别处再存一份标题**——两份就会分叉。

库自己的文案（右键菜单、视图模式名、「移至」、拖动标签、无障碍名）在 `Locales/*.axaml`
（键 `Forge.Strings.*`），与 Semi 的 `SemiTheme.Locale` 同一机制：

```csharp
ForgeThemeManager.ApplyLocale(app, CultureInfo.CurrentUICulture);
```

自带 13 种语言，与 Semi.Avalonia 对齐（`ForgeThemeManager.SupportedLocales`）：
en-US、zh-CN、zh-Hant、ja-JP、ko-KR、de-DE、fr-FR、es-ES、it-IT、nl-NL、pl-PL、ru-RU、uk-UA。
回落按语言前缀，不分地区（`de-AT` → de-DE，`fr-CA` → fr-FR）；中文按文字分（`TW/HK/MO/Hant` → zh-Hant，其余 → zh-CN）；没对应的 → en-US。
每份字典的键集由 `ForgeLocaleTests.Every_shipped_locale_has_exactly_the_english_keys` 锁死，加键必须 13 份一起加。

没装就是英文。想改哪句，在自己的资源里重定义同名键；不走 XAML 的宿主可整套给 `ForgeStrings.Override`。

### 5.3 图标

面板的 `Icon` 是 `object`，三种东西都收：

| 你给的 | 库怎么办 |
|---|---|
| `Geometry` | 直接画（等比缩放居中），颜色跟着状态走 |
| `Control`（`MaterialIcon`、`Image`、任何控件） | 挂成子元素，摆到图标位上由它自己画；库把当前前景色写在 `Foreground` 上，**继承 Foreground 的图标控件会跟着主题明暗与激活态变色** |
| `null` | 条带按钮画 `ForgeIcons.DefaultToolWindow` 那个空框；编辑区标签页**不画**（文件是什么类型只有你知道） |

库自带的 `ForgeIcons` 只有它自己要用的那几个（关闭、图钉、更多、分屏、默认图形），
按 16×16 画、显示时缩放到审出来的图标区（条带 20 / 紧凑 16，编辑区标签页 16）。
**领域图标你自己给** —— 比如 LDVision 用的是它既有的 Material.Icons。

编辑区标签页的图标从 `EditorTabViewModel.Icon` 来，`Open(panel)` 会自动从面板上取。

⚠ **图标控件不能共享**：一个 Avalonia 控件只能有一个父，两个面板拿同一个实例，
第二个挂不上去。每个面板 `new` 一份 —— 图标控件是轻量对象，别为它做缓存。
（放 `Geometry` 没有这个限制，它是不可变的绘图数据，随便共享。）

### 5.3b 往面板标题条上加东西：两个位，按"有没有固有宽度"选

| 挂载点 | 位置 | 宽度谁说了算 | 放什么 |
|---|---|---|---|
| `ForgeControl.HeaderButtonsExtension` | 标题条**右侧**，内置那两颗左边 | **库**：一律排成 `ForgeMetrics.HeaderButtonSize` 见方 | 只放图标按钮 |
| `ForgeControl.HeaderTitleAdornmentExtension` | **标题后面**、内容标签之前 | **控件自己**（量出来多宽就多宽），标签起点跟着往右让 | 只读标识、角标这类有固有宽度的东西 |

```csharp
frame.HeaderButtonsExtension        = id => id == "CamList" ? [new ForgeHeaderButton { Icon = ForgeIcons.Find }] : null;
frame.HeaderTitleAdornmentExtension = id => id == "FocusMeasure" ? _cameraTag : null;
```

⚠ **别拿右侧那条工具栏放"图标 + 一行字"**：它不问控件量出来多宽，
一律按 24 见方排；字会溢出格子压在旁边的按钮上（LDVision 实机撞过，
现象是标题条右端一堆字叠在按钮上）。判据是**放的东西有没有固有宽度**，
不是"想放左边还是右边"。

⚠ 两个位都是**每次同步问一次**：同一个面板请返回同一个控件实例（或按 id 缓存），
否则每次重画都在造新控件。

⚠ 标题后缀的可用宽度 = 标题右边到右侧按钮左边之间**还剩多少**。挂上来的控件要自己会缩，
写死 `Width` 的在窄面板上会坚持自己的宽度并溢出。它排在内容标签之前，
两者都有的窄面板上标签能用的地方会相应变少。

⚠⚠ **别拿横排 `StackPanel` 当容器**：它给子控件的可用宽度是**无限**（Avalonia 与 WPF 同），
会把这里传下去的"还剩多少"整个吃掉，于是文字按自然宽度报尺寸、重新溢出到按钮上。
给里面的文字设个 `MaxWidth` 来刹车是假的 —— 那个数既会在宽面板上把内容白白切短，
又在窄到不足那个数时照样兜不住。用 `DockPanel`（图标 Dock 左、文字填满）
或带约束的 `Grid`：它们会把剩余宽度如实传下去，够就按自然宽度、不够才截断。
这条由 `HeaderTitleAdornmentTests.面板窄时按剩余空间量_不许压到右侧按钮上` 守着。

### 5.4 编辑区

```csharp
var editor = new EditorAreaViewModel();
editor.Open(new ImageDocument("cam-1"));              // 继承 EditorPanel 的面板
editor.Area.Split(editor.Area.CurrentGroup, isVertical: true);

var control = new ForgeEditorControl();
control.Attach(editor);                               // 等价于 control.Area = editor
frame.EditorContent = control;                        // 挂进中间那块
```

规则（都照上游，见 [编辑区](../upstream/编辑区.md)）：
关掉一页之后**默认回到左邻居**（不是右邻居）；标签页上限 30，
超限先关预览页，**固定住的永远不被挤掉**；分屏只把**选中那一页**带过去。

⚠ `EditorTabViewModel.Content` **放数据不要放控件**：分屏之后同一页会同时开在两个组里，
一个 Avalonia 控件不能挂在两个父容器下。放数据由你的 DataTemplate 各渲染一份。

**编辑区的底色**由 `Forge.ExpUi.EditorBackground` / `Forge.Islands.EditorBackground` 两个键给
（同其余颜色，重定义即覆盖、明暗各盖各的）。上游让编辑区比工具窗口深/浅一档，那是给
**满屏文字**的 IDE 定的；宿主的编辑区若常是一整块空画布（图像视口这类），那一档差在暗色下
会读成一个黑洞 —— 想让它与面板同色，覆盖这个键即可，不必去改库里的配色。
分屏叶子跟着同一个键走，不会出现"分屏之后半边亮半边暗"。

### 5.4b 编辑区的两个回调

文档是有资源的（相机会话、图像帧、订阅），所以这两个必须接：

```csharp
editorVm.TabClosed      += (_, tab) => (tab.Content as IDisposable)?.Dispose();
editorVm.ActiveTabChanged += (_, tab) => _activeDocument = tab?.Content;
```

`TabClosed` 对应上游 `EditorWindow.kt:759` 的 `fileClosed` 广播，
`ActiveTabChanged` 对应 `EditorWindow.kt:232-241` 的 `TabsListener.selectionChanged`。
**库不替你 Dispose** —— 内容是你的对象，同一个会话可能还被别处引用着。

### 5.4c 编辑区背板：一张文档都没开时露出来的那一层（可选）

```csharp
control.BackplateFactory = () => new Border
{
    Width = 260, Height = 110,                                  // 与掩码同比例
    Background = watermarkBrush,                                // 颜色跟主题走
    OpacityMask = new ImageBrush(mask) { Stretch = Stretch.Fill },
};
```

**别把彩色 logo 直接摆上去**（第一版就是，一眼就丑）：它带着卡片底、渐变和品牌色，
摆在一片空地上比周围任何东西都重。VS Code / Rider 那种是**单色轮廓** ——
存一张只有 alpha 的掩码图，拿它当 `OpacityMask`，颜色交给主题的一把刷子，
明暗两档各是各的灰而图只存一张。弱化也归颜色管，别叠 `Opacity`。

是个**工厂**而不是一个控件：分屏之后每个叶子都要一份，而一个 Avalonia 控件只能有一个父。
可以在 `Attach` **之后**再配（宿主的外观本来就是建好控件才补的），已经建出来的组会当场跟上。

⚠ **它只在这一组一张文档都没开时才画。**直觉上背板该一直铺着、开了文档自然被盖住 ——
但**文档内容允许透明底**（编辑区底色本来就是给它们当底用的，见 5.4），
一直画的话它会从正文底下透出来，表现为"图像四周一圈水印"。

背板不接鼠标（库替你设了 `IsHitTestVisible = false`），点在空白处仍然只是"点进编辑区"。

### 5.5 存档：布局持久化，从零到全

用户拖过的面板宽度、开合状态、编辑区的分屏与标签顺序，重启后要还在 —— 这一节把
存、读、坏档、版本升级四件事一次讲完。**活例在 `samples/Piccolo.Forge.Sample.Mvvm`**，
本节每段代码都能在那里找到运行着的原文。

#### 存了什么、没存什么

| 存 | 不存（为什么） |
|---|---|
| 每块面板：在哪条边、哪半区、宽窄（weight）、开没开、什么形态（停靠/浮动…） | 面板的**内容与图标** —— 那是宿主的对象，塞不进 XML；恢复时从登记里来 |
| 面板标题条上内容 tab 的**顺序**（用户拖过的） | 面板**有哪些** —— 存档只描述摆放，名单永远以宿主 `Add` 了什么为准 |
| 编辑区：分屏树（谁和谁分、比例）、每组的标签页（id / 标题 / 钉住 / 预览）、选中页 | 标签页的**内容** —— 同上，恢复时按 id 由宿主认领（见 contentFactory） |

这个分工是设计出来的：**存档描述"摆成什么样"，宿主决定"有什么"** ——
所以版本升级换了面板名单，存档不会把界面弄坏（后面有表）。

#### 一站式：ForgeLayoutSerializer

整份布局一对调用（对位 Dock 的 `DockSerializer`）。完整的启动/退出接线长这样，
以 Avalonia 桌面应用为例：

```csharp
public partial class App : Application
{
    // 存到哪是宿主的事。常见选择：每用户数据目录（多用户/免管理员权限）。
    private static string LayoutPath => Path.Combine(
        Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
        "你的应用名", "layout.xml");

    public override void OnFrameworkInitializationCompleted()
    {
        if (ApplicationLifetime is IClassicDesktopStyleApplicationLifetime desktop)
        {
            var vm = new MainViewModel();          // 构造里做完全部 Add（① 顺序要求，见下）

            if (!vm.TryRestoreLayout(LayoutPath))  // ② 读：成功恢复 / 失败走默认，必居其一
                vm.OpenDefaultLayout();

            desktop.ShutdownRequested += (_, _) => vm.SaveLayout(LayoutPath);   // ③ 存

            desktop.MainWindow = new MainWindow { DataContext = vm };
        }
        base.OnFrameworkInitializationCompleted();
    }
}
```

装配处（MainViewModel）里对应的两个方法，各一行库调用：

```csharp
public bool TryRestoreLayout(string path) =>
    ForgeLayoutSerializer.TryRead(path, Shell, Editor, CreateEditorContent);

public void SaveLayout(string path)
{
    Directory.CreateDirectory(Path.GetDirectoryName(path)!);   // 目录可能还不存在
    ForgeLayoutSerializer.Write(Shell, Editor).Save(path);
}
```

**① 顺序是硬要求：恢复必须在所有面板 `Add` 完之后。** 存档里只有摆放没有内容，
`RestoreLayout` 拿着存档里的 id 去**已登记的面板**上套 —— 早于登记调用不报错，
只是什么都套不上（存档里的 id 一个都认不出，全被当成"已删掉的面板"忽略）。
把登记放构造、恢复单独成方法，先后就天然分开了。

**② 读失败不抛，返回 `false`。** 三种情况同一个出口：文件不存在（首次启动）、
XML 解析不了（存档坏掉）、根元素不认识（别家的文件）。调用方唯一要做的事就是
`false` 时走默认摆放 —— 存档出任何问题都**不该挡住启动**。

**③ 什么时候存。** `ShutdownRequested` 覆盖正常退出（关窗口、系统关机）。要注意它
**覆盖不了**进程被杀（任务管理器结束、崩溃）—— 在意这种场景就在用户改完布局后延时存
（或提供"保存布局"菜单项，同一个 `SaveLayout`）。

#### contentFactory：编辑区内容怎么回来

编辑区存档里只有标签 id 与树结构。恢复时库把树搭好，然后拿着每个 id 来问宿主：
"这一页的内容给我"。

```csharp
private static object? CreateEditorContent(string id) => id switch
{
    "readme"                          => new ReadmePanelViewModel(),
    var f when File.Exists(f)         => OpenDocument(f),   // id 就是文件路径的场合
    _                                 => null,              // 认不出来：这一页被丢掉
};
```

- 返回对象 → 这一页恢复，内容就是它（是 `IEditorPanel` 的话图标一并带上）；
- 返回 `null` → 这一页**被丢掉并报回**（`Editor.Restore` 的返回值是丢掉的 id 清单）——
  与上游一致：IntelliJ 解析不到文件时 warn + 跳过（`EditorsSplitters.kt` 的
  `resolveFileOrLogError`），不会因为一页认不出让整个恢复失败；
- 不给 factory → 所有页都留着、内容为空 —— 适合"内容按需惰性创建"的宿主。

新加一种页，factory 的 switch 里补一行 —— 忘了补的症状是那种页重启后消失（被当成
认不出的丢掉），日志里能看到报回的 id。

#### 存档长什么样（示意）

标签与属性名照抄上游 IntelliJ（`window.xml` 的 `window_info` / `anchor` / `side_tool` /
`weight`…；编辑区的 `splitter` / `split-proportion` / `leaf` / `file`），
**只写与默认值不同的属性**，所以默认摆放的存档几乎是空的：

```xml
<forge-layout version="1">
  <tools>
    <layout>
      <window_info id="Project" weight="0.28" visible="true" />
      <window_info id="Structure" side_tool="true" />
      <window_info id="Terminal" anchor="bottom" visible="true" />
    </layout>
  </tools>
  <editor>
    <splitter split-proportion="0.6">
      <split-first><leaf><file id="readme" /></leaf></split-first>
      <split-second><leaf><file id="notes" pinned="true" /></leaf></split-second>
    </splitter>
  </editor>
</forge-layout>
```

（示意，属性以实际写出的为准。）好处有二：肉眼可诊断 —— 用户报"布局乱了"，
让他把这个文件发来一看便知；与上游语义对齐 —— 每个属性在 IntelliJ 源码里有出处可查。

#### 埋进自己的设置文件（不单独落盘）

已经有一份设置 XML / 想把布局跟着设置一起存的，用 `XElement` 重载：

```csharp
// 存：把根元素挂进你的设置树
settingsRoot.Add(ForgeLayoutSerializer.Write(shell, editorVm));

// 读：从你的设置树里取出来喂回去（解析你自己文件的 try/catch 归你）
if (settingsRoot.Element(ForgeLayoutSerializer.RootTag) is { } layout)
    ForgeLayoutSerializer.TryRead(layout, shell, editorVm, CreateEditorContent);
```

#### 只存一块 / 两块分开放

底下分块的序列化器照旧公开，语义与门面完全相同：

```csharp
var tools  = shell.SaveLayout();                          // <layout>…</layout>
var editor = EditorLayoutSerializer.Write(editorVm.Area); // ⚠ 根元素名随分屏与否变，
                                                          //   自己包一层具名容器再存
shell.RestoreLayout(tools);                               // 返回真正套上去的 id
editorVm.Restore(editor, id => ReopenDocument(id));       // 返回被丢掉的 id
```

门面替你做的三件事，自己拆开就要自己做：具名容器（编辑区根元素不定名）、
坏档 try/catch、"两块其一缺失时跳过而不是失败"。

#### 版本升级：库替你兜住的三条

| 情况 | 行为 |
|---|---|
| 存档里有这一版**已经删掉**的面板 | 忽略（`RestoreLayout` 只认已登记的 id，返回真正套上去的那批） |
| 存档里**没有**这一版新加的面板 | 保持它的默认摆放 |
| 编辑区某一页宿主认不出来了 | `contentFactory` 返回 `null`，那一页被丢掉并报回 |

所以「升级后布局全乱」和「升级后起不来」这两种事不会发生。存档坏掉（XML 解析不了）
走 `TryRead` 的 `false` 出口 —— 记条日志、退默认布局，别让它挡住启动。

#### 排查速查

| 症状 | 多半是 |
|---|---|
| 恢复后什么都没变 | 恢复调早了（在 `Add` 之前）—— 存档里的 id 全被当成已删面板忽略 |
| 某种编辑区页重启后消失 | `contentFactory` 的 switch 没这种页 —— 看 `Restore` 报回的 id |
| 恢复成功但又变回默认 | 恢复成功后还执行了默认摆放（`OpenDefaultLayout` 该在 `false` 分支里） |
| 正常退出没存上 | 存挂在了窗口 `Closing` 之类的早期事件上被绕过 —— 用 `ShutdownRequested` |
| 进程被杀后丢布局 | `ShutdownRequested` 不覆盖强杀 —— 改完布局延时存一份 |

## 7. 两个容易踩的坑

**别自己缓存面板控件再手工塞进去。** 控件的复用由 `frame.Sync()` 负责：
状态一变它只改属性、只增删父子关系，**不重建任何已有控件**。
这正是内容能安全地放实时画面 / 图表 / 日志的原因——
有用例数着「内容控件被构造了几次」钉住这条。

**别把明暗钉死。** `Appearance.FollowThemeVariant` 默认开着，跟着宿主走。
钉死一套的结果是系统切浅色时「软件其余部分变白、外壳还是黑的」，中间一道硬边。
真要自己控制，把开关关掉再赋控件的 `Palette`。
